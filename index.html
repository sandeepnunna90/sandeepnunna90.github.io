Built on my own · Vitalog · 2026 course capstone

Lab results a patient can bring to the doctor, and the doctor can check.

People with chronic conditions see several specialists, and their lab results end up scattered across portals and paper. Vitalog reads each report, tracks every biomarker over time, and writes a one-page summary for the next appointment, where each claim links back to the document it came from.

Python and the Claude API, with strict type checking and an evaluation set of synthetic lab reports that come with their correct answers.

One gateway for every model call

Nothing calls Claude directly. Guardrails, versioned prompts, eval logging and citation checks live in one place, so a model or prompt change is one edit.

Claims that can be checked

Every number in a summary or answer must match a stored record, or the output is refused. Summaries also check dates; free-text answers don't yet, and qualitative wording isn't checked. An LLM judge is the planned next step.

Three confidence bands

High-confidence extractions are accepted, the middle band goes to human review, and low-confidence results are rejected instead of guessed. The thresholds are still being calibrated.

MCP-first

Claude Desktop is the interface: a FastMCP server with six tools and OAuth 2.0 sign-in, deployed and talking to Supabase.

Decisions I made, and why

OCR before vision models

Textract reads each report first, with Claude vision only as a fallback. Vision models can invent plausible numbers when a scan is unclear, and that failure is hard to spot.

Plain code where code will do

Unit conversion, name lookup, dates and math run as ordinary code. The model only does what needs a model: reading reports and writing summaries.

Refuse rather than half-check

If a claim fails verification, the generator tries once more, then returns a fixed refusal. Nothing goes out partly verified.

Test data with the answers built in

Synthetic lab reports are rendered from data, so each one carries its correct answers. Every eval run is logged with its commit and prompt versions, and adversarial reports (a phone photo, a multi-page report, an unusual unit) each document the failure they test.

How it's tested

  • 20 adversarial prompts aimed at the safety layer, from requests for direct medical advice to prompt injection.
  • A test that fails if any code calls the model outside the gateway.
  • A test for retry-once-then-refuse when a claim fails verification.
  • Adversarial lab reports, each with its correct answers and a note on the failure it tests.

Known limits: the eval set is small, free-text answers don't yet check dates or qualitative wording, and it runs for a single demo patient. All listed in the architecture doc ↗
